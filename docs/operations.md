## 1. 힙이 아니라 힙 밖이 넘쳤다

**증상.** 2026-07-24 배포가 반복 크래시 끝에 Railway에서 제거됐다. `OutOfMemoryError` 스택이
어디에도 남지 않았다. 빌드 실패도 아니었다 — 이미지 다이제스트는 정상이었다.

**확인.** 메트릭으로 원인을 좁혔다. 한도 512MB에서 정상 상태 **412MB(80.5%)** 로 몇 시간 평평하다가,
재배포 버스트에서 **654MB(128%)** 로 튀어 커널에 죽었다. 곡선이 평평했으므로 누수가 아니라
**여유가 없었던 것**이다.

**뿌리.** JDK 17은 컨테이너를 인식해 힙을 512MB의 25%(=128MB)로 잡는다. 그런데 **제한되는 건 힙뿐이다.**
Tomcat 200 스레드·Metaspace·코드 캐시·다이렉트 버퍼는 전부 서버급 머신을 가정한 기본값이고
합계 상한이 없다. 그래서 힙이 절반도 안 찬 채로 총 RSS가 한도를 넘고, JVM이 자기 오류로
인지하지 못한 채 프로세스만 사라진다.

**대응.** 힙은 원인이 아니었으므로 `MaxRAMPercentage`는 기본값과 같은 25를 **의도적으로 명시**하고
(늘리지 않았다는 기록), 힙 밖을 조였다.

```dockerfile
-XX:MaxRAMPercentage=25        # 원인이 아니므로 유지 — 명시는 의도의 기록
-XX:+UseSerialGC
-XX:TieredStopAtLevel=1        # C2 JIT off. 병목은 OpenAI 지연이라 처리량을 포기해도 체감차 없음
-Xss512k
-XX:MaxMetaspaceSize=160m
-XX:ReservedCodeCacheSize=64m
-XX:MaxDirectMemorySize=64m
-XX:+ExitOnOutOfMemoryError    # 힙이 진짜 차면 즉시 죽여 재시작 — GC 스래싱보다 낫다
```

Tomcat 스레드 200 → 20, Hikari 커넥션 10 → 5도 같이 낮췄다. 데모 트래픽은 사실상 단일 사용자다.

**결과.** 512MB 컨테이너 실측 **335.7MB → 233.7MB (-102MB).** 같은 비율이면 Railway 정상 상태가
412MB → 약 285MB(56%)가 되어 버스트 여유가 20%에서 44%로 늘어난다.

**교훈.** 컨테이너 메모리 사고에서 힙 그래프만 보면 아무것도 안 보인다. 봐야 할 것은 RSS이고,
JVM에게 "네가 쓸 수 있는 총량"을 알려주는 단일 스위치는 없다.

## 2. 트랜잭션 안에서 LLM 을 기다렸다

**증상.** 2026-09-04, 문의 135가 `NEW` 상태로 영구히 남았다. 유저 포털은 `NEW`면 타이핑 버블을
띄우고 폴링에 타임아웃이 없어서, 고객에게는 **영원히 "분석 중"** 으로 보였다.

**뿌리.** `InquiryAnalysisService.analyze()`가 `@Transactional`이었고, 그 안에서 ReAct 에이전트가
LLM을 최대 8라운드 호출했다. **DB 커넥션을 십수 초 붙잡은 채 외부 API를 기다리는 구조**였다.
`route()`의 Slack 웹훅도 같은 트랜잭션 안에 있었다.

14.2초 실행 중 Railway Postgres가 절전에 들어가 커넥션이 끊겼고, 커밋도 롤백도 못 했다.

곁가지로 `AnalysisLogService.logFailure`가 `REQUIRES_NEW`였다 — 실패 시 바깥 커넥션을 쥔 채
두 번째 커넥션을 요구한다. prod 풀 5, async 풀 8이라 동시 실패가 겹치면 서로 막힐 수 있었다.

**대응.** 트랜잭션을 셋으로 잘랐다 — **읽기 / 에이전트 실행 / 결과 저장**. 외부 호출은 트랜잭션
밖에서만 한다.

```
[읽기 tx]  →  에이전트 실행 (tx 없음, LLM·Slack)  →  [저장 tx]
```

처음에는 `TransactionTemplate`으로 나눴다. `@Transactional` 두 개로 쪼개면 **같은 빈 안의 호출이
프록시를 타지 않아 트랜잭션이 조용히 안 걸리기** 때문이다. 이후 `InquiryAnalysisRecorder`를
별개 빈으로 분리하면서 프록시가 정상 동작하게 되어 `TransactionTemplate`을 걷어냈다.

→ [ADR-0009](adr/0009-no-external-calls-in-transactions.md)

**교훈.** "트랜잭션 안에서 외부 호출 금지"는 아는 규칙이지만, 어기고도 로컬에서는 아무 문제가 없다.
DB가 절전에 들어가는 환경에서야 드러났다. 그리고 규칙을 지키려 메서드를 쪼갤 때
**같은 빈 안의 자기 호출은 프록시를 안 탄다**는 함정이 하나 더 있다.

## 3. 실패한 분석을 주워 올릴 훅이 없었다

**증상.** 분석이 실패하면 그대로 끝이었다. `@Async` 이벤트가 유일한 트리거였기 때문에,
그 이벤트가 실패하면 다시 시도할 경로가 어디에도 없었다.

**대응.** `AnalysisRetryScheduler`가 주기적으로 실패·유실 분석을 집어 올린다.

- 상태를 **DB(분석 로그)에 두므로** 배포와 재시작을 넘어 살아남는다
- 프로세스가 죽어 `RUNNING`으로 남은 것도 같은 쿼리로 주워진다
- 재시도 상한 3회. 소진해도 버리지 않고 **상담사에게 도달시킨다** — 문의를 잃지 않는 게 원칙이다
- `@ConditionalOnProperty`로 끌 수 있다. 운영에서 잠시 내리는 스위치이자, DB 없이 컨텍스트만
  로딩하는 테스트에서 기동을 깨지 않게 하는 장치다

→ [ADR-0006](adr/0006-never-lose-an-inquiry.md) · [ADR-0009](adr/0009-no-external-calls-in-transactions.md)

**교훈.** 비동기 이벤트를 유일한 트리거로 두면 실패가 곧 유실이다. 상태를 DB에 남기고 쓸어담는
스위퍼를 하나 두는 것으로 대부분의 유실 경로가 닫힌다.

## 4. 프롬프트 캐시는 에러 없이 비용만 올린다

에이전트 루프는 매 스텝마다 전체 메시지를 재전송한다. 8스텝이면 시스템 프롬프트가 8번 나간다.
OpenAI는 요청 접두부가 이전과 동일할 때만 프롬프트 캐시를 적용하는데, **캐시가 깨져도 에러가 나지
않는다 — 비용만 조용히 오른다.** 그래서 관측 대상으로 삼았다(`LlmResponse.cacheReadTokens`).

**실측 (2026-09-06, gpt-4.1-mini).** 동일 시스템 프롬프트로 4회 연속 호출:

| 회차 | prompt | cached | 적중 |
|---:|---:|---:|---:|
| 1 | 3,324 | 0 | — (첫 호출이 캐시를 만든다) |
| 2 | 3,313 | 2,944 | 88% |
| 3 | 3,315 | 3,072 | 92% |
| 4 | 3,311 | 3,072 | **92%** |

대화를 늘려가며(앞을 고치지 않고 뒤에만 append) 재요청하면 캐시 구간도 따라 자란다:

| 스텝 | 메시지 | prompt | cached |
|---:|---:|---:|---:|
| 1 | 2 | 3,314 | 3,072 |
| 2 | 4 | 4,102 | 3,072 |
| 3 | 6 | 4,890 | 3,968 |
| 4 | 8 | 5,678 | 4,736 |

**읽을 것 셋.**

- **캐시는 한 스텝 뒤처져 따라온다.** 스텝 2에서 cached가 안 늘어난 것은 새로 붙인 2개 메시지가
  방금 처음 보낸 내용이기 때문이다. 그건 스텝 3에서 들어온다. 매 스텝 정가로 나가는 건
  "직전에 새로 붙인 분량"뿐이다.
- **128토큰 블록 단위다.** 2,944 → 3,072은 둘 다 128의 배수다. 프롬프트가 3,324인데 3,072까지만
  캐시되는 이유도 같다.
- **뒤에 붙이는 건 공짜, 앞이나 중간을 고치면 그 뒤가 전부 날아간다.** 캐시 대상은 "시스템 프롬프트"가
  아니라 요청 맨 앞부터의 연속 구간이다.

**설계에 반영된 것.** `[오늘] YYYY-MM-DD`를 시스템 프롬프트가 아니라 **사용자 메시지**에 넣는다.
접두부에 있었으면 날짜가 바뀔 때마다 3,300토큰 전체가 무효가 된다. `PromptFactoryTest`의
`systemPromptIsDeterministic`이 접두부에 시각·랜덤·요청별 ID가 섞이지 않도록 고정한다.

**교훈.** 히스토리를 중간에서 잘라내거나(sliding window), 앞쪽에 요약을 끼워넣거나, 시스템
프롬프트에 타임스탬프를 넣는 순간 캐시가 통째로 무효가 된다. 셋 다 흔한 최적화라서 더 위험하다.

## 부록: 측정하고 바꾸지 않은 것

에이전트는 OpenAI native function calling 대신 자체 ReAct 프로토콜(`action`/`actionInput` JSON)을
쓴다. native로 옮기면 응답 파싱 실패가 구조적으로 사라지므로 전환을 검토했고, **먼저 실패 빈도를
운영 로그에서 재봤다.**

```sql
SELECT count(*) FILTER (WHERE error_message LIKE 'Failed to parse agent response%') AS 파싱실패,
       count(*) FILTER (WHERE analysis_status = 'FAILURE')                          AS 전체실패,
       count(*)                                                                     AS 전체
FROM inquiry_analysis_log;
```

2026-04-12 ~ 09-04 전체 11건에서 **파싱 실패 0건.** 유일한 실패 1건은 LLM이 아니라
`could not execute statement [An I/O error occurred while sending to the backend.]` — 위 2번의
DB I/O였고, native로 옮겨도 사라지지 않는 종류다.

표본 11건은 작아서 "0%"가 아니라 "관측되지 않았다"에 가깝다(rule of three로 95% 상한 ≈ 27%).
다만 **전환을 정당화할 증거가 없는 반면 비용은 확정적**이다 — `thought` 필드가 어드민 화면에
걸려 있고, 다중 관심사 분해 규칙이 그 필드에 의존하며, `ChatMessage`/`LlmResponse` 확장과
테스트 4개 파일 재작성이 따라온다. 그래서 옮기지 않았다.

대신 그 전환의 준비 작업(입력 record를 JSON Schema의 단일 출처로 삼기)만 먼저 해두어,
근거가 생기면 스키마 계층을 다시 만들지 않아도 되게 했다.
