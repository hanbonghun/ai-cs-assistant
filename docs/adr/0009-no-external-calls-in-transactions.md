# 0009. 트랜잭션 안에서 외부 호출을 하지 않는다

- 상태: 채택
- 결정 시점: 2026-09-04

## 맥락

`InquiryAnalysisService.analyze()` 가 `@Transactional` 이고, 그 안에서 ReAct 에이전트가 LLM 을
최대 8라운드 호출했다. DB 커넥션을 십수 초 붙잡은 채 외부 API 를 기다리는 구조였다.
`route()` 안의 Slack 웹훅도 같은 트랜잭션에 있었다.

2026-09-04 에 터졌다. 14.2초 실행 중 Railway Postgres 가 절전에 들어가 커넥션이 끊기고,
커밋도 롤백도 못 해서 문의 135 가 `NEW` 로 남았다. 유저 포털은 `NEW` 면 타이핑 버블을 띄우고
폴링에 타임아웃이 없어 고객에게 영구히 "분석 중" 으로 보였다.

부수적으로 `AnalysisLogService.logFailure` 가 `REQUIRES_NEW` 였다 — 실패 시 바깥 커넥션을 쥔 채
두 번째 커넥션을 요구했다. prod 풀은 5, async 풀은 8이라 동시 실패 시 서로 막힐 수 있었다.

## 결정

트랜잭션을 세 조각으로 나눈다 — 읽기 / 에이전트 실행 / 결과 저장. 외부 호출은 트랜잭션 밖에서만
한다.

1. 분할 수단은 private 메서드 안의 `TransactionTemplate` 이다. `@Transactional` 두 개로 나누면
   같은 빈 안의 호출이 프록시를 타지 않아 **트랜잭션이 조용히 걸리지 않는다.** 새 빈을 만드는 것은
   프록시 사정 때문에 클래스를 만드는 일이라 하지 않았다
2. Slack 알림은 커밋 후에 보낸다. 알림만 나가고 커밋이 실패하는 순서를 없앤다. 알림에는 저장
   단계가 돌려준 엔티티를 넘긴다 — Slack 메시지가 `getCategory()`/`getUrgency()`/
   `getAiDraftAnswer()` 를 읽으므로 낡은 detached 엔티티를 넘기면 null 로 나간다
3. 저장 단계는 문의를 재조회하고 상태를 다시 검증한다 — 십수 초 사이에 상담사가 종료했을 수 있다.
   단일 트랜잭션이 공짜로 주던 보호다
4. 분석 잡의 진행/실패는 `InquiryStatus` 가 아니라 `inquiry_analysis_log.analysis_status` 의
   `RUNNING` 으로 둔다. `InquiryStatus` 는 "고객 대화가 어디까지 왔나" 의 축이고 분석 잡 상태는
   다른 축이다. 섞으면 목록 필터·상세 분기·유저 포털·폴링 루프가 전부 따라 움직인다.
   행은 새로 넣지 않고 제자리에서 뒤집는다 — "최신 로그" 를 읽는 곳들이 과도 상태를 보면 안 된다
5. 실패와 유실은 `@Scheduled` 스위퍼가 2분마다 주워 최대 3회 재시도한다. 소진하면 ADR 0006 대로
   `[자동 합성]` 브리핑으로 상담사에게 올린다

## 포함하지 않은 것: Hikari 설정

`keepalive-time` / `max-lifetime` 조정은 넣지 않았다. HikariCP 는 커넥션을 빌려줄 때 이미 검증한다
(`aliveBypassWindow` 500ms 밖이면 `isValid()` 확인 후 교체). 사고는 "죽은 커넥션을 빌렸다" 가
아니라 **"14.2초간 쥐고 있는 동안 커넥션이 죽었다"** 였다 — 어떤 풀 설정으로도 안 막히고
트랜잭션을 짧게 만드는 것만이 막는다.

`keepalive-time` 이 기여하는 지점은 다르다. `minimum-idle: 1` 이라 유휴 커넥션 하나를 계속 핑하게
되어 Railway Postgres 가 애초에 절전에 안 들어간다 — 원인 클래스를 없애는 대신 DB 를 계속 깨워두는
값을 치른다. 데모 환경의 시간 제한을 그대로 쓰기로 했다.

## 결과

- 커넥션 점유가 14.2초에서 수십 ms 로 떨어진다. 절전 타이밍에 걸릴 창이 사실상 사라진다.
  `FakeLlmClient` 가 호출 시점에 `TransactionSynchronizationManager.isActualTransactionActive()`
  를 기록하므로 이 성질이 테스트로 잠긴다
- `logFailure` 의 `REQUIRES_NEW` 를 뗐다. 풀 데드락 소지가 사라진다
- 실패가 관측된다. RUNNING 이 남으면 프로세스가 죽은 것이고, FAILURE 가 최신이면 재시도 대상이다
- "영구히 분석 중" 이 원리적으로 불가능하다. 상태가 항상 `NEW` 를 벗어나므로 UI 폴링 타임아웃은
  도달 불가 코드가 되어 추가하지 않았다
- 대가 1: 이 코드베이스의 다른 곳은 `@Transactional` 을 쓰는데 여기만 `TransactionTemplate` 이다.
  경계가 호출 지점에서 안 보인다 — 대신 조용히 실패하지 않는다
- 대가 2: 저장 단계에서 상태가 변해 결과를 못 쓰는 경우가 생긴다. 에이전트 실행 비용을 버리지만,
  이미 종료된 문의를 덮어쓰는 것보다 낫다
- 대가 3: 추가 질문 라운드도 분석 로그를 남기게 되어 대시보드의 총 분석 건수·평균 지연·평균 토큰에
  포함된다. "분석 실행 횟수" 로는 정확해지지만 이전 숫자와 비교할 수 없다. 대신 지금까지 유실되던
  추가 질문 라운드의 에이전트 스텝과 토큰이 관측된다
- 대가 4: 저장 단계에서 문의가 이미 종료돼 결과를 못 쓰는 경우, 그 시도의 RUNNING 행이 남는다.
  스위프 대상 상태(`NEW`/`PENDING_CUSTOMER`)에서 빠져 재시도되지 않으므로 무해하지만, 분석 로그에
  스텝이 안 채워진 행 하나가 남는다
- 대가 5: 스위퍼는 단일 인스턴스를 전제한다. 소프트 락(fresh RUNNING 거부)뿐이라 다중 인스턴스로
  가면 `select … for update` 가 필요하다
- 대가 6: `@Scheduled` 빈은 `spring.main.lazy-initialization` 을 우회해 즉시 생성된다. DB 없이
  컨텍스트 로딩만 확인하는 테스트가 DataSource 오토컨피그를 빼고 도는데 그 컨텍스트에서 기동이
  깨졌다. `app.analysis.retry.enabled` 로 끌 수 있게 했다 — 운영에서 잠시 내리는 스위치로도 쓴다
