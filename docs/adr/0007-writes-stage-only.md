# 0007. 에이전트의 쓰기 툴은 staging 만 하고, 실행은 승인 표면에서만 일어난다

- 상태: 채택
- 결정 시점: 2026-09-03

## 맥락

환불 요청이 오면 AI 는 "담당자가 확인 후 처리해 드리겠습니다"로 끝냈고, 상담사는 시스템 밖에서
환불을 처리했다. 시스템은 환불이 됐는지·얼마가 나갔는지·누가 승인했는지 몰랐다.
반대로 에이전트에게 환불 실행 툴을 주는 것은 돈이 나가는 일이라 받아들일 수 없었다.

## 결정

쓰기 툴은 **제안만** 만든다. 실행 권한은 승인 표면 하나에만 둔다.

- `stage_refund` 는 `staged_change` 행을 `PENDING` 으로 저장하고 끝난다.
  성공 문구에 "아직 실행되지 않았으며 상담사 승인이 필요합니다"를 명시해 모델이 실행 완료로 오인하지 않게 한다
- 제안 시점에 가드레일 4종을 검사한다 — provenance(이번 대화에서 실제 조회한 주문인가) · 금액 · 주문 상태 · 중복
- 제안이 접수되면 `needsHumanReview` 를 코드로 강제한다
- `StagedChangeApprovalService` 가 유일한 실행 경로다. 승인 시점에 가드레일을 **다시** 검사한다 —
  제안 시점과 승인 시점 사이에 주문 상태가 바뀔 수 있다

## 결과

- 결정 이력(누가·언제·왜·AI 제안 금액 대비 실제 금액)이 `staged_change` 에 남아 별도 감사 테이블이 필요 없다
- 동시 승인을 두 겹으로 막는다: `@Version` 이 같은 행에 대한 두 결정을, `order_id where status='APPROVED'`
  unique 부분 인덱스가 **서로 다른 제안 두 건이 같은 주문을 이중 환불하는 것**을 막는다.
  `@Version` 만으로는 후자가 열려 있었다
- 문의 상태 머신(`InquiryStatus`)을 건드리지 않는다. 답변 확정과 환불 승인이 독립이라
  상담사가 환불만 승인하고 답변은 더 고칠 수 있다
- 한계: DB 두 건은 한 트랜잭션이지만 mock 주문 변경은 그 밖이다. 실행을 마지막에 두었을 뿐,
  실제 결제 시스템이면 아웃박스가 필요하다
- 한계: 승인 엔드포인트에 인증이 없다. `decidedBy` 가 클라이언트에서 오므로 감사 컬럼이 상수다
